# 进度与决策记录

> 从 `AGENTS.md` §4 展开。两类记录解决两个不同的问题：
> **进度页回答“现在做到哪了”，决策日志回答“当初为什么这么做”。** 不要混在一份文件里。

## 1. 进度页：`docs/进度.md`

### 1.1 模板（照抄，五节不许改名）

````markdown
# 项目进度

## 当前状态
- 最新 commit: a9f06cf (feat: 交付 T-01..T-12)
- 测试状态: 144 passed, 1 warning
- Lint: 通过

## 已完成
- [x] <能演示或能验收的东西>（怎么验：<命令或操作>）
- [x] <同上>

## 进行中
- [ ] <一件事>（60% —— 卡在哪 / 下一步动作）
- [ ] <一件事>（0% —— 还没开始，前置是 X）

## 已知问题
- <现象> → <影响> → <谁在跟>

## 下一步
1. <一天内能做完的一步>
2. <一天内能做完的一步>
````

### 1.2 四条硬规则

1. **`当前状态` 三行必须是跑出来的，不许估。** 命令就是这三条：

   ```powershell
   git log --oneline -1          # 取短哈希 + 标题
   python -m pytest -q           # 取尾行的 “144 passed”
   python -m ruff check .        # 取 “All checks passed!”
   ```

   写“测试基本通过”= 无效记录。

2. **`已完成` 只写能演示 / 能验收的。** 判断标准：能不能用一条命令、一次点击、一张截图证明它存在。
   “写了识别模块”不算；“上传一张截图能返回 3 条证据，`/demo` 里能点”算。

3. **`进行中` 最多 3 项，每项必须带百分比或明确卡点。** 超过 3 项说明同时在开三条战线，先收敛。
   百分比不许拍脑袋：用“还剩几个子任务 / 总共几个”算。

4. **整页 ≤40 行（含 front-matter）。** 超了不是加内容，是删——把细节挪到 `docs/reports/` 的回执里。

### 1.3 什么时候改

| 时机 | 改哪几节 |
|---|---|
| 每完成一个任务（提交后、开 PR 前） | `当前状态` 三行 + `已完成` 加一条 + `进行中` 减一条 |
| 发现新坑 / 被阻塞 | `已知问题` 加一条（现象 → 影响 → 谁在跟） |
| 每周五对齐会 | 全文复核一遍，`下一步` 重排，超过两周没动的项删掉或降级 |
| 里程碑达成（第 2 周四条命令全绿、第 8 周能 compose 演示） | `已完成` 补一条并注明“怎么验” |

### 1.4 反模式（写了等于没写）

| 反模式 | 为什么不行 | 改成 |
|---|---|---|
| 把 `docs/tickets/` 的 TODO 全抄进来 | 10 天后没人看得懂哪里是真进度 | 只留“现在正做的那 1–3 项” |
| “分页功能 80%” | 80% 不可验证，也没说卡在哪 | “分页 80%：边界用例 `test_pagination_edge_case` 返 500，正在查空结果集” |
| 按人分组（“A 在做 X，B 在做 Y”） | 人一动就过期，且看不出项目整体 | 按里程碑 / 需求分组，人名写在括号里 |
| 三个月不更新 | 读者会以为项目停了，或以为这页不可信 | 每周五复核一次；过期即删 |
| 写成日报 / 感想 | 没人读，且挤压真正的事实 | 只写事实 + 判据 |

## 2. 决策日志：`docs/decisions/ADR-000N-<短名>.md`

### 2.1 什么时候必须写

满足任意一条就写：

- 改技术栈、加依赖、换框架；
- 改 `app/schemas/` 的契约（字段、类型、含义）；
- 改门禁（新增一条 CI 检查、改 DoD、改必检项）；
- 改目录边界 / 模块职责（谁调谁、谁能改什么）；
- 推翻旧决策（写“取代 ADR-000X”，不要回去改原文）；
- 影响超过一个人的流程（分支策略、评审方式、汇报格式）。

**不用写**：局部实现选择（用 dict 还是 list）、命名、临时调试手段、可随时撤销的试验。

### 2.2 模板

````markdown
---
title: ADR-0005 <一句话标题>
owner: 队长
status: review
last_updated: 2026-11-10
summary: <一句话结论>
audience: agent
---

# ADR-0005 <一句话标题>

## 背景
<什么情况下必须做这个决定；列出 2–3 个真实约束（时间、人力、依赖）>

## 决策
<选了什么，一句话能说清；涉及范围写清“只用于 X，不用于 Y”>

## 代价
<换来什么、付出什么；至少写一条“以后会痛的地方”>

## 替代方案
<考虑过但没选的 1–2 个，各一句为什么不选>

## 推翻条件
<什么现象出现时才值得重开这个话题；没有触发条件 = 这条决策会永远挂着>
````

### 2.3 三条纪律

1. **只追加，不改写。** 决策变了就写新 ADR，旧的在文末补一行「已被 ADR-000N 取代」。
2. **写完同步摘要表**：在 `docs/agents/技术栈与架构决策.md` §2 加一行（结论 + 推翻条件），否则没人看得到。
3. **一次决策一个文件。** 不要把三个决定塞进一个 ADR——将来只推翻其中一个时，你没法写“取代”。

## 3. 交付前四问（30 秒自查）

1. `docs/进度.md` 的 `当前状态` 三行，是这个提交之后跑出来的吗？
2. 我这次做的事，在 `已完成` 里能用一句话 + 一条验证方式说清吗？
3. 我这次有没有做“影响别人”的决定？有 → ADR 写了吗、摘要表加了吗？
4. 进度页还是 ≤40 行吗？

四问有一问答不上，就别开 PR。

## 4. 跟门禁的关系

进度页与 ADR **不进门禁**（`docs.py check` 只校验 front-matter、索引、死链、合规、覆盖），因为写得好坏无法机器判定。
靠两处兜住：

- PR 描述里必须写一句「进度已更新：是（改了哪几处）/ 否（为什么）」；
- 队长的 3 分钟抽检会问“这个功能现在在进度页的哪一行”——答不上来就是不达标。
