# ADR-0009 上传体积与类型的三层防护

- 状态：已采纳（2026-11-28）
- 影响范围：所有上传接口、`app/main.py` 中间件链、`app/pipelines/vision/ocr.py` 的常量来源

## 1. 背景

改造前的情况：

1. `detect_audio` / `detect_image` 两个接口都是**先 `await file.read()` 把整个文件读进内存**，
   再交给下游判断格式。一个大文件会在"判断格式"之前就把内存吃掉。
2. 音频**没有任何体积上限**；图片虽有 4MB 上限，但同样在"读完之后"才检查，起不到保护作用。
3. 音频只看扩展名（`asr.py` 的 `SUPPORTED_SUFFIXES`），把压缩包改名 `.wav` 会真的进到 wav 解析里。
4. 除了这两个接口，别的接口（如 `/kb/cases`）没有任何请求体上限。

## 2. 决策

**分三层，各管一段，缺一层都能被绕过：**

| 层 | 位置 | 管什么 | 拦不住的 |
|---|---|---|---|
| ① 中间件预检 | `BodySizeLimitMiddleware`（`app/main.py` 注册） | `Content-Length` 超 12MB → 进路由前 413 | 伪造 Content-Length、分块传输 |
| ② 读时限量 | `read_limited()`（`detect.py` 调用） | 只读 `limit+1` 字节，多出的一个字节就是超限证据 | 类型是假的（内容不对） |
| ③ 领域魔数 | `has_magic()`（`detect.py` 调用） | wav 必须 `RIFF`；图片必须 PNG/JPEG 签名 | 体积（已在第 ② 层拦住） |

**上限值（唯一定义在 `app/core/limits.py`）：**

| 常量 | 值 | 依据 |
|---|---|---|
| `MAX_AUDIO_BYTES` | 8MB | 16k/16bit 单声道 wav ≈ 4 分钟，覆盖单通通话片段 |
| `MAX_IMAGE_BYTES` | 4MB | 沿用 `ocr.py` 既有口径，不扩大也不缩小 |
| `MAX_REQUEST_BYTES` | 12MB | 取较大值再留 4MB 余量给 multipart 边界 |

**错误码**：新增 `file_too_large`（413）；类型不符复用已有的
`unsupported_audio_format` / `unsupported_image_format`（415）。**原有错误码一个不改**。

## 3. 为什么这样选（而不是别的）

- **为什么不用 `app.mount` 或 `MAX_CONTENT_LENGTH` 式全局变量？**
  FastAPI 没有内置的请求体上限，社区常见做法是 `BaseHTTPMiddleware` 读完整 body。
  我们选了**不读 body 的纯 ASGI 中间件**：唯一开销是一次头部判断，也不引入缓冲语义。
- **为什么上限常量不能有两份？**
  `ocr.py` 原来自己写 `4 * 1024 * 1024`。如果上传口用 4MB、领域层用 8MB，
  就会出现"路由放行、领域层报错"的怪现象，且排查时看不出是哪个数字在生效。
  所以规定：**只有 `app/core/limits.py` 定义，别处只能 import**。
- **为什么这一单不顺手做音频切分？**
  `asr.py` 当前是 `energy-vad-only` 骨架，**没有转写 backend，切分结果无处可送**。
  待 ASR 接入且具备 VAD 静音切点、重叠去重、时间戳拼接能力后，另行开单（T-13）。
  本条是硬约束：**本单禁止加入任何降级切分逻辑**。

## 4. 代价

- `app/main.py` 加了一行中间件注册——这是本单唯一碰入口文件的地方。
- 中间件对 `Content-Length` 非法（负数/非整数）会返回 400；正常客户端不会遇到。
- 分块传输（`Transfer-Encoding: chunked`）的大文件，第 ① 层看不到长度，靠第 ② 层在读时拦住。
  这是有意的分层取舍：不让中间件缓冲请求体。

## 5. 什么情况下推翻本决策

- 需要支持 >8MB 的音频（例如整通电话录音）→ 改 `MAX_AUDIO_BYTES` 并在这里追加一条记录，不要另起常量。
- 需要支持 WebP / HEIC 截图 → 扩大 `IMAGE_MAGIC` 并同步 `ocr.py` 的签名判断。
- 需要按用户或接口做差异化限额（如付费用户更大）→ 这是新需求，另开 ADR，不要在本文件里改规则。
