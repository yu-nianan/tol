# 任务回执：运行时库（T-14）已交付

## 做了什么

`app/pipelines/storage.py` 落地四张表（`sessions` / `messages` / `alerts` / `meta`），启动 `init_db()` 幂等建表并写入 `schema_version=1`；
`engine` 的会话与告警改为"内存热缓存 + 库为真相"，重启后 `_hydrate()` 自动回读；告警查询改走 `engine.get_alert()`（先内存再库）；
`/api/v1/stats` 计数改为从库里数，并新增 `messages`。实测：两轮检测后重启服务，`GET /report/s_demo` 与 `GET /alerts/A460bf7049a` 均正常返回。

## 没做完 / 已知问题

- **没做**：画像、冷却、白名单（T-09 / FR-2.6 归 B）、报告快照表（T-11）。
- 已知：`messages` 表只存文本与 level/score，存不下音频/图片的 URI——等 T-13 统一预处理定稿后再补列。
- 已知：并发写靠 SQLite 的 `timeout` 兜，压测还没做（风险低，单进程演示够用）。

## 下次接手要知道什么

- 入口：`from app.pipelines.storage import get_storage`（进程内单例，`lru_cache`）；`RESET_DB=1` 才会清库，平时启动绝不删表。
- 表结构在 `storage.py` 顶部 `SCHEMA` 常量；**加字段先升 `SCHEMA_VERSION` 并写迁移分支**，别直接改 `CREATE TABLE`。
- `evidence` / `notifications` / `last_decision` 存 JSON 字符串（`json.dumps(..., ensure_ascii=False)`），读出来再给 Pydantic。
- 引擎里唯一的写入点是 `_persist()`；新增落库请改它，不要在别处直接调 storage，否则重启后会丢一半状态。
- 库文件在 `data/app.db`，被 `.gitignore` 忽略；测试一律用 `tmp_path`。
