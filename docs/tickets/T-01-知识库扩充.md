## 1. 背景（为什么做这件事）

反诈助手的判断力，一半来自规则和模型，**另一半来自"见过多少案例"**。
现在知识库只有 10 个剧本、20 条案例，后果是：

- 判别模块只能覆盖最常见的几类骗局，稍微换个说法就判不出来；
- 检索模块（BM25）样本太少，召回质量测不出来，"检索有没有用"无法证明；
- 答辩时评委问"你的知识库哪来的、覆盖多少类"，现在答不上来。

这一单不涉及模型、不涉及算法，是**纯数据工程**——最适合第一个上手做，因为做完马上能看到分数和召回的变化。

## 2. 目标（做完之后，什么会不一样）

| 指标 | 现在 | 目标 |
|---|---|---|
| 剧本（`app/kb/scripts.json`） | 10 类（S01–S10） | **15 类**（新增 S11–S15） |
| 案例（`app/kb/cases.json`） | 20 条（C001–C020） | **50 条**（新增 C021–C050） |
| 每类剧本的案例数 | 0–3 条不等 | 每类 **≥3 条** |
| 知识库形状测试 | 无 | `tests/knowledge/test_kb_shape.py`，随 `pytest` 一起跑 |
| 检索自检（自己搜自己） | 无测量 | Top-1 命中本剧本 **≥85%**，结果写进回执 |

## 3. 要做的三件事（按顺序，别跳）

### 3.1 新增 5 个剧本（S11–S15）

照抄 `scripts.json` 里 S01 的结构，**4 个阶段固定不变**（`contact / authority / isolate / transfer`），每阶段：

- `signals` **≥3 条**话术关键词（要口语，要能出现在真实对话里；
  不能写"诈骗"这种元描述词——那是判断结论，不是话术特征）；
- 阶段 `weight` 必须**递增**（接触 < 立威 < 隔离 < 诱导转账），直接沿用 0.3 / 0.55 / 0.75 / 0.95；
- `risk_base` 取 80–95；
- `advice` **≥2 条**，写"用户该怎么办"，不写"系统怎么实现"。

要新增的 5 类：

| 编号 | 剧本名 | 提示（话术落点） |
|---|---|---|
| S11 | 快递丢件理赔 | 快递丢失、丢件、双倍赔付、加微信退款、屏幕共享、验证码 |
| S12 | 虚假投资平台（外汇/期货） | 外汇/期货、分析师喊单、内部消息、入金、出金失败、补仓、保证金 |
| S13 | 冒充熟人（AI 语音/视频） | 换号、声音、视频通话、AI 换脸、不方便接电话、急用钱转账 |
| S14 | 虚假招聘（打字员/配音员） | 招聘、在家办公、日结、押金/培训费/会员费、连环任务不能提现 |
| S15 | 短信钓鱼链接（ETC/违章/医保） | 失效、已停用、点击链接、限时处理、重新认证、补缴 |

> **2026-11-07 队长批准的口径修正**：初版要求的 S11“冒充客服退款”、S12“虚假投资理财”、
> S13“冒充领导/熟人”、S14“刷单返利”，现有 `scripts.json` 的 S04/S03/S07/S02 已经分别覆盖。
> 再建 4 个同义类会让检索自检（每条案例原文搜自己）出现同义类互抢 Top-1，直接跌破 85%。
> 因此改为上表 5 个**不重复的手法子类**，保留原主题的“新手法”覆盖面，避开与已有类抢召回；
> 旧 10 类的 `id` 与 `name` 均未改动。

### 3.2 案例补到 50 条（C021–C050）

每条格式（照抄现有 20 条）：

```json
{
  "id": "C021",
  "script_id": "S11",
  "title": "快递丢件双倍赔付",
  "level": "L2",
  "text": "您好，您的快递在运输中丢失，我们这边给您双倍赔付，请添加客服微信办理退款。"
}
```

硬性要求：

- `script_id` 必须是 S01–S15 里真实存在的；**每个剧本 ≥3 条**；
- `level` 要 **L1/L2/L3 都有**（不要全填 L3，那说明你在"贴标签"而不是在描述）；
- `text` 20–80 字，写**受害者听到的原话**，不要写成案情摘要；
- **至少 5 条带噪声**：错别字、多余空格、全角标点、夹杂表情/符号——用来测鲁棒性（这些是加分项，答辩能讲）；
- `id` 唯一、连续编号。

### 3.3 加一个形状测试

新建 `tests/knowledge/test_kb_shape.py`，至少覆盖 5 条断言：

1. `scripts.json` 里剧本数 == 15，且 id 连续无重复；
2. 每个剧本的 `stages` 恰好 4 个，`weight` 严格递增；
3. 每个 stage 的 `signals` ≥3 条且无重复；
4. `cases.json` 里案例数 == 50，每个 `script_id` 都存在，每类 ≥3 条；
5. 每条案例的 `text` 长度在 20–80 之间。

> 测试只校验"形状"，不校验"内容对不对"——内容对不对由第 9 节的抽查看。

## 7. 怎么和 agent 交流（照这 5 条，能省一半时间）

| # | 做法 | 反例（别这样） |

| 1 | **一次只给一件事**："把 S11 加到 scripts.json，4 阶段各 3 个信号词" | "帮我完善一下知识库" |
| 2 | **贴原文**：完整报错、文件路径、你跑的命令 | "它报错了" |

还有两条经验：

- 让它**先给你看 2 条样例**（1 条剧本 + 1 条案例），你确认口径对了再让它批量写——批量写错 30 条比写错 2 条难改得多；
- 它写的内容你**看不懂没关系，但要能判断"像不像真人说的话"**。像"该行为涉嫌违法诈骗"这种，是法律文书，不是受害者的电话录音，退回去重写。

## 8. 怎么交接（交付流程，缺一步都算没做完）

1. **建分支**：`git switch -c feature/knowledge-kb-expand`
2. **提交**（一次只做一件事）：
   ```
   feat(knowledge): 补 S11–S15 剧本与 30 条案例
   test(knowledge): 加知识库形状校验
   docs(knowledge): 补任务回执
   ```
3. **推 + 开 PR**：`git push -u origin feature/knowledge-kb-expand`，然后在网页开 PR，
   PR 描述里**粘贴四条命令的完整输出**（不是最后一行）。
4. **写回执**：`docs/reports/2026-11-0X-knowledge-A.md`，从 `docs/reports/_模板.md` 复制，
   四节必须有：**做了什么 / 没做完 / 下次接手要知道什么 / 怎么验收**。
5. **等 CI**：`check` 和 `docs` 两个检查变绿后，**你自己点 Merge**（不需要任何人批准）。
6. **回报三行**（发群里，不发小作文）：
   ```
   做了什么：知识库补到 15 剧本 / 50 案例，检索自检 92%
   验收命令：check.ps1 -Task all + python scripts/docs.py check
   结果：全绿
   ```

> 推不上去（没权限/没网）：把文件留在本地，在回执里写「文件在 `<绝对路径>`，未推送，原因：`<报错原文>`」。
> **禁止假装已上传。**

## 9. 怎么审查（队长 5 分钟清单，队员也可以照着自查）

| # | 看什么 | 怎么看 | 不合格的表现 |
|---|---|---|---|
| 1 | **范围** | `git diff --stat` | 动了 `app/pipelines/**` 或 `app/schemas/**` → 直接打回 |
| 2 | **命令** | 跑第 6 节三条命令 | 任何一条红；或 PR 里没贴输出 |
| 3 | **数据真实性** | 随机抽 3 条 `text` 念出来 | 像法律条文/像新闻稿，不像电话里说的话 |
| 4 | **有没有作弊** | 搜 `case_id` / 硬编码关键词 | 检索逻辑里出现写死的 id 或"如果包含X就返回Y" |
| 5 | **覆盖度** | 按 `script_id` 分组计数 | 某类只有 1 条、或 30 条全填 L3 |
| 6 | **回执** | 看四节是否都写了 | "没做完"一栏写"无"但命令没全绿（说明在瞒） |

审查**不看**：代码风格、命名好不好听、注释多不多——这些由 ruff 和你们的约定兜底，人不用管。
