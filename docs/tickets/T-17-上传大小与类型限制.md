# 任务单：别让一个超大文件或改名的假文件把服务拖垮

## 1. 背景（为什么做这件事）

- 对应需求：`FR-1.1`（多模态输入入口）、`NFR-7`（安全：上传类型与大小限制）
- **先说结论**：现在上传音频和截图时，程序会先把整个文件读进内存，然后才判断格式。
  于是拿一个 500MB 的文件去试，机器会先卡住，几秒后才报"格式不对"；拿一个压缩包改名叫
  `截图.png`，程序也会先读进来再报错。**这两种情况都能把演示当场搞挂。**
- 另外，图片原本有 4MB 上限，但那是"读完之后再检查"，起不到保护作用；音频**完全没有上限**。
- 这件事不做，演示当天有人传错一次大文件，服务就得重启。

## 2. 目标（做完之后，什么会不一样）

- 传一个超过上限的文件：**立刻**收到"文件过大"的提示，服务不受影响，下一个请求照常。
- 传一个改过扩展名的假文件：收到"只支持 wav / PNG / JPEG"的提示，不会进入解析流程。
- 正常的小文件：行为和现在一模一样（wav 仍然因为没有语音识别模型而如实报告"转写未接入"，
  截图仍然如实报告"OCR 未接入"），**不许因为加了限制改变原有结果**。

底线：做不到的（例如暂时判断不了分块传输的真实大小）就如实返回错误码，不许假装成功。

## 3. 输入 / 输出样例（写死，不要"大概"）

| 你拿什么试 | 期望看到 |
|---|---|
| 9MB 的 wav 录音 | 立即返回"文件过大（上限 8MB）"，服务随后仍能正常响应别的请求 |
| 5MB 的截图 | 立即返回"文件过大（上限 4MB）" |
| 内容只有几个字母、但叫 `test.wav` | 返回"不是合法的 wav 文件"，不进入切分 |
| 一个压缩包、改名叫 `test.png` | 返回"只支持 PNG / JPEG"，不进入识别 |
| 正常的小 wav（1 秒静音） | 和现在一样："已切出 N 段，但未接入转写" |
| 正常的 1x1 截图 | 和现在一样："已解析，但未接入文字识别" |
| 13MB 的任意请求体打到别的接口 | 立即返回"请求体过大"，不进入该接口 |

## 5. 不许做的事（本次特有）

- **禁止顺手加入任何降级切分逻辑**，理由见下面这段（原文保留）：

  > `asr.py` 当前为 `energy-vad-only` 骨架，无转写 backend，切分结果无处可送。
  > 待 ASR 接入且具备 VAD 静音切点、重叠去重、时间戳拼接能力后，另行开单。

- 不许新增依赖（这是纯标准库能做完的事）。
- 不许把上限常量在第二个地方再定义一遍（`MAX_AUDIO_BYTES` 只能有 `app/core/limits.py` 一处）。
- 不许把"限制"做成"模模糊糊地截断文件"——超限必须报错，不许静默截取前 N MB 继续处理。
- 不许因为加了检查而改动原有错误码（`asr_not_configured` / `ocr_not_configured` 必须原样保留）。

## 8. 交付时会问的三个问题（提前想好）

1. **能直接用吗？** 能——上限是 8MB 音频 / 4MB 图片 / 12MB 请求体，覆盖手机录音与微信截图。
2. **为什么只做到上限、不做切分？** 因为 `asr.py` 还是 `energy-vad-only` 骨架，切出来没地方送；
   先做切分等于给一个空管子加压。等 ASR 接入后再开单。
3. **出问题会怎样？** 超限与伪造都返回明确错误码，服务不会崩；正常文件行为完全不变。
