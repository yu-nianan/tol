# 任务单：<一句话说清要做什么，用大白话>

> **用法**：复制本文件 → 改名为 `T-<模块>-<短描述>.md` → 把九节填满 → 发给负责这块的队友（和他的智能体）。
>
> **填不满就别开工**：没有第 6 节"怎么算做完"的任务，等于没定义。
>
> **语言要求（最重要的一条）**：这张单子是**给队友看的执行说明书**，不是技术方案。
> 写"现在会怎样、做完会怎样、你拿什么试、看到什么算对"，**不写**字段名、环境变量名、正则、参数取值、代码片段。
> 一句话检验：**队友的父母看得懂大方向，队友本人照着能开工。**

> **front-matter 三行必填**（决定需求覆盖表长什么样）：
>
> - `covers: [FR-1.2]` —— 我**主责**的需求，验收只看这几条
> - `supports: [FR-1.4]` —— 我只提供依赖、不负责验收（可留空 `[]`）
> - `depends_on_task: [T-01]` —— 必须先做完的**任务单**（写 T-编号，不写文件名）
>
> 一条需求只能有一张任务单写进 `covers`，写重了文档检查会红。

---

## 1. 背景（为什么做这件事）

- 对应需求：`FR-2.3`（一句话说它是什么）
- **先说结论：现在是什么样、卡在哪。** 用"你拿手机试一下就会看到"的方式写，不写代码原因。
- 让读者明白：**这件事不做，哪一步会断**。

## 2. 目标（做完之后，什么会不一样）

- 从"用户/队友能感知到"的角度写，不写内部结构。
- 例：不是"新增 xxx 模块"，而是"拿微信里的语音也能直接试，不用先转格式"。
- 最后补一句**底线**：什么情况下允许"明确说做不到"，但不许假装成功。

## 3. 输入 / 输出样例（写死，不要"大概"）

**不要贴 JSON 字段。用一张表：你拿什么试 → 期望看到什么。**

| 你拿什么试 | 期望看到 |
|---|---|
| <一份真实素材> | <人眼能验证的现象> |
| <一份边界素材> | <不会静默失败 / 有明确提示> |

## 4. 允许修改的路径（超出即越界）

```
<你负责的目录>/**
<你的测试目录>/**
```

**顺手写清"不要碰什么"**：不要在别人的模块里改逻辑，缺东西就提申请。

## 5. 不许做的事（本次特有）

- 挑 3–5 条**这次最容易犯**的，不要抄全局禁令（那是 `AGENTS.md` 的事）。
- 例：不许装新库、不许假装成功、不许把真实素材留在仓库、不许在这一步做判断、不许吞错误。

## 6. 验收（做到什么算完）

**流程一句话**：照老规矩提 PR，四条命令全绿——命令不用背，`AGENTS.md` §2 里写着。

**演示清单**（做完拿这几份素材各试一遍，结果发群里，截图或一行字都行）：

- [ ] <素材 A> → <看到什么算对>
- [ ] <素材 B> → <看到什么算对>
- [ ] <素材 C> → <不会怎样>

## 7. 预计与截止

| 项 | 内容 |
|---|---|
| 负责人 | 队长 / A / B / C / D（写进 front-matter 的 `owner`） |
| 预计耗时 | <N> 天（每天 ≤3 小时） |
| 前置 | <哪张单子必须先交付，或写"无"> |
| 截止 | <周几 几点> |
| 卡住找谁 | @队长（什么情况必须来问，写清楚） |

## 8. 交付时会问的三个问题（提前想好）

挑读者**真会问**的，不要刁难式提问。常见三类：

1. **能不能直接用？**（拿真实素材试过没有）
2. **为什么只做到这一步？**（边界在哪、代价是什么）
3. **出问题会怎样？**（失败了会不会把演示搞砸）

## 9. 完成记录（负责的智能体填）

```
做了什么：<一句话>
验收：四条命令全绿 + 演示清单逐条试过（结果已发群）
结果：<全绿 / 哪条红，红在哪>
契约变更：无
```
