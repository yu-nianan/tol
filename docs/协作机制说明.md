# A30 技术规范落地包

> 配套文件：`repo-kit/`（直接拷进你们仓库根目录即可用）
> 适用：5 人队、只有队长有全栈基础、代码主要由各自的 AI 智能体产出。
> 一句话流程：**队长先定（公告）→ 开一场认领的会 → 20 分钟培训 → 第 2 周跑通验收**。

---

## 1. 为什么这件事不该靠开会

三句话：

1. **会议产出共识，你们缺的是执行。** 队员对"FastAPI 还是 Django"形成不了真实意见，能形成的意见只有"这块我愿不愿意做、做不做得完"——那是分工，不是技术。
2. **技术判断只有一个人有判据。** 让没有判据的人投票，结果是把责任摊薄：出了事谁都不认。
3. **规范的正确性不靠讨论，靠跑通。** 第 2 周三个 Hello demo 一跑，选型对不对、契约够不够用，当场就知道。

所以把所有事分成三类：

| 类型 | 例子 | 谁定 | 形式 |
|---|---|---|---|
| 技术判断 | 选型、目录、契约、边界 | 你 | 单点决定 + 公告 + 48h 异议期 |
| 人的承诺 | 谁认领哪块、每周几小时、不会什么 | 全员 | **唯一必须开的会** |
| 知情与培训 | 三条命令怎么跑、任务单怎么填 | 你 | 20 分钟演示，不讨论 |

> 判据：**讨论能改变结果的，开会；讨论只会增加噪音的，你定完公告。**

## 2. 第一步：发第一条公告（选型表）

在群里发这一条（可直接复制，改占位符即可）：

> 【技术选型公告 · 48 小时异议期】
> 下面是 A30 的技术底座，已按"会不会用 / 八周跑不跑得通 / 演示够不够看 / 出问题有没有人兜"四条判据选定。
> 有异议请在 **周五 20:00 前** 回复：哪一条 + 改成什么 + 为什么（基于上面四条判据）。
> 到期无异议即生效，之后不再复议；要改就按"决策记录"流程走。

| 槽位 | 选定 | 理由（一句话） | 备选 |
|---|---|---|---|
| 后端框架 | FastAPI + Pydantic | 自动出 `/docs`，接口契约即代码，零基础也能看懂请求示例 | Flask |
| 前端 | React + Vite（手机优先响应式） | 生态最大，智能体生成质量最高 | Streamlit（保底演示版） |
| 大模型 | 一家主用 + 一家备用（走 OpenAI 兼容接口） | 换供应商只改 base_url，不改代码 | 本地 7B（仅离线演示） |
| 语音转写 | FunASR（paraformer-zh） | 中文电话场景表现好，本地可跑 | faster-whisper |
| 图片识别 | PaddleOCR（装不上就 RapidOCR） | 中文截图识别准 | 云 OCR API |
| 检索 | FAISS + BM25（RRF 融合） | 零部署、够快、可解释 | Chroma |
| 部署 | Docker Compose | 一条命令起来，就是"可运行程序" | 本地 venv + 启动脚本 |

配套第二条（同一天发）：

> 【协作约定公告 · 48 小时异议期】
> 仓库根目录已放 `AGENTS.md`（智能体须知）、`OWNERS.md`（谁能改哪）、`scripts/check.ps1`（三条检查命令）、`docs/tickets/模板.md`（任务单）。
> **规则只有一条：PR 里必须贴三条命令的完整输出，没有就不合并。**
> 谁看不懂 `AGENTS.md` 里任何一句，直接问，别猜。

## 3. 第二步：认领会议（唯一必开的会，60 分钟）

### 会前 10 分钟准备

- [ ] 打印一张空白认领表（见 3.3），A4 横版
- [ ] 白板/投屏写好 5 组模块与一句话职责
- [ ] 群里发一句：**"今晚只定一件事：谁做哪块。技术细节我来定，不用你们判断。"**

### 3.1 分钟级脚本

| 时间 | 环节 | 你做什么 | 关键动作 |
|---|---|---|---|
| 0–5′ | 定规矩 | 只讲三句：今天只定分工 / 技术我来定 / 认领=承诺 | 不许展开技术讨论，跑题记到"下次议题" |
| 5–15′ | 过架构 | 5 组模块，每组一句话，不解释实现 | 每屏 2 分钟，讲完就问"这块听懂了吗" |
| 15–40′ | 认领 | 逐组问三个问题（见 3.2），当场填表 | 没人认领就当场指派，别留悬念 |
| 40–48′ | 边界 | 问"哪块你肯定不做"、"谁需要配对" | 写进表里，避免后面互相等 |
| 48–55′ | 定节奏 | 定周会时间、三条命令什么时候开始跑 | 从下周起，每人每周必须交一个能跑的东西 |
| 55–60′ | 复述 | 每人一句："我做 X，周五交 Y" | 不一致当场纠正 |

### 3.2 认领时只问三个问题

1. **这块你愿意做吗？**（意愿）
2. **你每周能投几小时？**（现实，写数字，不写"尽量"）
3. **这块里你完全不会的是什么？**（边界，写下来才知道要不要配对）

> 不要问"你觉得这块难不难"——零基础的人判断不了难度，只会说"应该还行"，然后第 4 周崩。

### 3.3 认领表（打印这张，手填）

| 模块组 | 包含 | 一句话职责 | 负责人 | 每周小时 | 不会的部分 | 首个可跑版本 |
|---|---|---|---|---|---|---|
| 入口与管道 | M1–M4 | 把文本/录音/截图变成结构化证据 | | | | W2 |
| 判断 | M5–M8 | 判类型、判阶段、打分、给解释 | | | | W3 |
| 处置 | M9–M11 | 分级预警、通知监护人、出报告 | | | | W4 |
| 知识 | M6+M12 | 剧本库、案例库、入库与检索 | | | | W3 |
| 底座 | M13–M15 | 网关、评测、前端、打包部署 | | | | W2 |

### 3.4 三种卡壳场景怎么处理

| 场景 | 你的处理 |
|---|---|
| 没人认领某块 | 当场指派："这块先归你，周五交一个能跑的骨架，不会的部分我们下周看"——**先认领再谈能力** |
| 两人抢同一块 | 按"谁先说出这周能交什么"定；另一人做该块的**测试与素材**（同样是交付物） |
| 认领了但明显做不完 | 立刻切成两半，另一半给别人或你自己兜；不许"先试试" |

### 3.5 主持台词（照念即可）

- 开场：**"今天不开技术讨论会。技术我定，你们只需要认领和说清时间。"**
- 认领时：**"认领不是'我试试'，是'我周五交一个能跑的东西'。做不到现在说。"**
- 有人问技术细节：**"这个问题记下来，会后我发文档；现在先定分工。"**
- 收尾：**"每人一句：我做哪块、周五交什么。说不清就还没定。"**

## 4. 第三步：20 分钟培训（不是会，是演示）

对着投屏做一遍，让每个人跟着敲：

| 分钟 | 做什么 |
|---|---|
| 0–3′ | 打开 `AGENTS.md`，指给他们看"只允许改这些路径"和"三条命令" |
| 3–8′ | 演示 `pwsh scripts/check.ps1 -Task lint`，故意写一个错，看它报错 |
| 8–14′ | 演示 `-Task test` 与 `-Task smoke`（先启动服务） |
| 14–18′ | 演示提 PR：把三条命令的输出整段粘进 PR 描述 |
| 18–20′ | 一句话总结：**"你们不需要看懂代码，只需要会贴命令输出。"** |

培训后发一条：

> 【自查清单】交付前自己跑一遍：`check.ps1 -Task lint` → `test` → `smoke`，三条全绿再提 PR。有一条红就别说"做完了"。

## 5. 第四步：第 2 周"跑通"验收

这是这套规范真正的考试，标准只有三条（对应三个 Hello demo）：

| 验收项 | 通过标准 | 谁来验 |
|---|---|---|
| 一个页面 | 打开能看到"粘贴短信 → 点检测 → 显示分数"，哪怕是假的 | 队长 |
| 一个接口 | `POST /api/v1/detect` 返回符合 `app/schemas/api.py` 的 JSON | 队长 |
| 一个脚本 | 能读 `data/` 里的 CSV 并输出统计（哪怕只有 100 行） | 队长 |
| 冒烟 | `check.ps1 -Task smoke` 三条全绿 | 机器 |

**跑不通才是正常的**——跑不通就改一条规范，改完记录到 `docs/decisions.md`。会开在"跑不通之后"，比开在"动手之前"有用十倍。

## 6. 五个规范文件怎么用

| 什么时候 | 用哪个 | 注意 |
|---|---|---|
| 每次派活 | `docs/tickets/模板.md` | 任务单必须写"允许改的路径"和"验收命令"，否则智能体会越界 |
| 智能体每次开工 | `AGENTS.md` | 第一句就让它读这个文件；它读不懂就说明文件写得太绕，改文件不改智能体 |
| 不知道谁能改 | `OWNERS.md` | 契约目录 `app/schemas/` 永远是"只读，仅队长" |
| 交付前 | `scripts/check.ps1` | 三条全绿；红了不许合并 |
| 合并时 | PR 模板 | 没贴输出 = 未完成，直接打回 |

修改规则（也写进 `AGENTS.md` 了）：**契约文件只有队长能改；任何人改契约，必须在群里说一句"契约变更：加了 X 字段"。**

## 8. 会被问到的四个问题（提前准备好答案）

| 他们问 | 你答 |
|---|---|
| "我们看不懂代码，怎么审查？" | 不审代码，审**命令输出**。三条命令全绿 + PR 贴日志，就算审过了。看不懂代码不等于没法验收。 |
| "智能体不听话、乱改文件怎么办？" | `AGENTS.md` 里写死了"只允许改这些路径"；越界就在 PR 里点出来打回。三次越界就把那条路径加进"禁止修改"清单。 |
| "这样是不是太严了？" | 严的只有一条：**PR 要贴输出**。其余都是"给你省事"的——没有它，联调那天通宵。 |
| "能不能先做，规范以后补？" | 可以，但只补一条：`AGENTS.md` + 三条命令。其余的等第一次联调失败再补，那时你们知道该补什么。 |

## 9. 这份包故意不做什么

- **不做完整的代码规范文档**（PEP8 那一套）——用 `ruff` 自动格式化，人不写规范。
- **不做评审会**——零基础团队开评审会只会变成"队长讲、大家听"。
- **不做需求变更流程**——八周的项目，变更靠群里一句话 + `decisions.md` 记一行就够。
- **不引入 CI 服务器**——本地 `check.ps1` 先跑；等有人能维护 workflow 再上 GitHub Actions。
