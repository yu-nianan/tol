# A30 多模态反诈助手 · 测试方案与用例

> 配套：`docs/A30-需求清单.md`（28 条 FR / 10 条 NFR / 11 项交付物）。
> 目的：**用"怎么测"把"要什么"钉死**。凡是写不出用例的需求，都还是模糊的——文末第七节列出了这类地方及建议口径。
> 说明：用例编号 `TC-模块.序号`；冒烟用例 `SMOKE-n`；优先级 P0 阻断主线 / P1 影响指标 / P2 体验问题。

---

## 一、测试策略

| 层次 | 测什么 | 谁来做 | 何时做 |
|---|---|---|---|
| 单元测试 | 打分器、实体抽取、JSON 校验、去重逻辑 | 写该模块的人 | 随代码提交 |
| 接口测试 | 每个 API 的正常 + 异常入参 | 模块负责人 | 每周 |
| 端到端（E2E） | 上传 → 判别 → 预警 → 通知 → 报告 | 全员 | 从第 5 周起每周一次 |
| 指标测试 | 准确率、误报、F1、时延、并发、稳定性 | 测试负责人 | 第 7 周集中跑 |
| 验收测试 | 按本文件逐条过，出测试报告 | 队长 | 交付前 |

原则：**每条 M 级需求至少 1 条用例；没有用例的需求视为未定义。**

## 二、测试环境与数据准备

| 项目 | 内容 | 责任人 |
|---|---|---|
| 服务环境 | 本机 Docker Compose（app + 向量库），端口固定 | 负责人 C |

## 五、指标用例（第 7 周集中执行）

| 编号 | 指标 | 方法 | 通过判据 |

## 七、测试暴露出的需求歧义（建议写回需求文档）

这一节是本文档的主要产出：**把模糊需求变成可判定的口径**。

| 需求原文 | 歧义 | 建议口径（写进需求） |
|---|---|---|
| 语音阻断 | 是拦电话还是提醒？ | 定义为"语音播报 + 一键挂断引导"，不承诺系统级拦截 |
| 响应时间 < 10s | 从哪算到哪？ | 从用户点击提交到前端出现结果；含降级路径，超时先出规则结果 |
| 准确率 > 90% | 在哪个集合上？ | 100 条测评集、融合输入子集、3 次投票，另附官方 20 条结果 |
| 误报率 < 5% | 什么算"正常社交"？ | 100 条含钱/转账/验证码的正常对话；纯寒暄不计入分母 |
| 连续运行无崩溃 | 跑多久、怎么判？ | 24h 连续跑批，进程存活 + 内存无持续增长 + 无未捕获异常 |
| 多轮上下文一致 | 几轮算多轮？ | 连续 5 轮，第 5 轮能正确引用第 1 轮信息 |
| 不少于 10 种诈骗剧本 | 怎么算"识别成功"？ | top1 类型命中即算对；混淆类别记入混淆矩阵 |
| 视频流输入 | 必须实时流吗？ | 支持上传短视频并抽帧即视为满足；实时流列为加分项 |
| 一键通报与远程干预 | "远程干预"做到什么程度？ | 通报 = 推送 + 回执；干预 = 打开带上下文的页面并可标记处置 |
| 个性化阈值 | 改阈值还是改分数？ | 统一为"阈值偏移"，同分不同级，便于解释与测试 |
