# 评估报告

> 本报告只写**跑出来的数**。每条数据下方都给了复现命令；没跑过的（如"连续 24 小时"）在
> §5 明确写"未验证"，不用估计值冒充实测值。

## 1. 评估口径

| 项目 | 口径 | 出处 |
| --- | --- | --- |
| 判别阈值 | 引擎判到 `Level.L2` 及以上才算「判为诈骗」 | `app/pipelines/knowledge/evalcheck.py:1-7` |
| 正 / 负类 | 测评集 `label=1` 为黑（诈骗），`label=0` 为白（正常） | 同上 |
| 指标 | 精确率 / 召回率 / F1 / 准确率，按混淆矩阵 TP/FP/TN/FN 计算 | 同上 |
| 测评集 | `app/kb/eval_set.csv` 40 条（黑白 1:1）；`app/kb/eval_set_official.csv` 20 条 | T-05 交付 |
| 时延口径 | HTTP 端到端耗时，含排队；取 P50 / P95 / P99 | `scripts/perf_run.py` |
| 压测口径 | 默认 **10 并发 × 600 秒**；判定线：成功率 ≥99% 且 P95 <10s | `scripts/perf_run.py` 默认值 |
| 稳定性口径 | 每个间隔打一条 JSONL（健康、检测、耗时、RSS、异常计数） | `scripts/guard_24h.py` |

## 2. 判别质量（F1 / 准确率）

| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `eval_set.csv` | 40 | 20 | 4 | 16 | 0 | 0.833 | 1.000 | **0.909** | **0.900** |
| `eval_set_official.csv` | 20 | 10 | 2 | 8 | 0 | 0.833 | 1.000 | **0.909** | **0.900** |

## 3. 时延与压测

### 3.1 短跑实测（3 并发 × 10 秒）

服务跑在 `docker compose up -d` 起的容器里（应用端口映射到宿主机 8000）：

```powershell
& .\.venv\Scripts\python.exe scripts\perf_run.py --base-url http://127.0.0.1:8000 --concurrency 3 --duration 10
```

实际输出：

```
压测口径：3 并发 × 10 秒
目标：http://127.0.0.1:8000/api/v1/detect/text
请求总数 1992，成功 1992，失败 0，成功率 100.00%
耗时(ms)：avg 14.99 | p50 13.52 | p95 31.02 | p99 32.26 | max 132.46
吞吐：198.88 req/s（成功请求 / 实际 10.016s）
判定：成功率≥99% PASS；P95<10s PASS
```

### 3.2 正式口径（未跑满）

- 正式口径是 **10 并发 × 600 秒**，判定线成功率 ≥99%、P95 <10s。
- 本次交付只跑了 3 并发 × 10 秒的短跑（上表）；**10 并发 × 10 分钟未跑**，原因是本机演示环境
  时间预算不足，不把短跑数字冒充正式压测结论。
- 复现正式口径：

```powershell
& .\.venv\Scripts\python.exe scripts\perf_run.py --concurrency 10 --duration 600
```

## 4. 24 小时守护（脚本已就绪，未跑满 24 小时）

`scripts/guard_24h.py` 默认每小时打一条 JSONL，写入 `data/guard/guard_24h.jsonl`；字段包含
`health_ok/health_ms/detect_ok/detect_ms/detect_level/rss_bytes/errors_total/failures_total`。
`--pid` 传入目标进程时采样其 RSS（Windows 用 `psapi.GetProcessMemoryInfo`，Linux 读 `/proc/<pid>/status`）。

短跑自检（间隔 1 秒 × 3 秒，目标为本地 uvicorn 进程 pid=34200）：

```powershell
& .\.venv\Scripts\python.exe scripts\guard_24h.py --base-url http://127.0.0.1:8001 --interval 1 --duration 3 --pid 34200
```

实际输出（末条）：

```
{"ts": 1794041109.587, "iso": "2026-11-07T16:45:09+08:00", "tick": 4, "health_ok": true, "health_ms": 20.48, "detect_ok": true, "detect_ms": 258.86, "detect_level": "2", "error": "", "rss_bytes": 59240448, "guard_rss_bytes": 27267072, "errors_total": 0, "failures_total": 0, "ticks_total": 4}
```

- 采样到的目标进程 RSS：`59,064,320 → 59,240,448` 字节（约 56.3 → 56.5 MiB），4 个点无异常增长；
- 守护进程自身 RSS 约 26.0 MiB；
- `errors_total=0`、`failures_total=0`，健康检查与检测请求全部成功。
- **连续 24 小时未跑**；上面只是脚本可用性的短跑自检。正式 24h 记录应跑
  `& .\.venv\Scripts\python.exe scripts\guard_24h.py`（默认 86400 秒）并保留生成的 JSONL。

## 5. 容器与换机复现

2026-11-07 实测（Docker Desktop 4.x，Linux 容器）：

```powershell
docker --version          # Docker version 29.5.3, build d1c06ef
docker compose version    # Docker Compose version v5.1.4
docker compose -f docker/docker-compose.yml up -d --build
docker compose -f docker/docker-compose.yml ps
```

结果：

- `docker-app-1` 状态 `Up (healthy)`，端口 `0.0.0.0:8000->8000/tcp`；
- `GET http://127.0.0.1:8000/health` 返回
  `{"status":"ok","version":"0.1.0","kb_scripts":15,"kb_cases":50,"llm_enabled":false,"asr_enabled":false,"ocr_enabled":false}`；
- `GET http://127.0.0.1:8000/` 返回 42,249 字节的演示页（`frontend/index.html`，由负责人 D 维护），
  说明镜像已把 `frontend/` 打进容器；
- 首次 `up` 时本机 Docker daemon 未启动，报
  `failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine`；
  启动 Docker Desktop 后重跑成功。另发现：宿主机 8000 端口被本地 uvicorn 占用时，
  compose 会出现"容器 healthy 但 ports 为空"的状态，停掉本地进程后重新 `up` 才有端口映射。

## 6. 未验证项与风险

1. **10 并发 × 10 分钟压测未跑**，只有 3 并发 × 10 秒短跑；正式结论待补。
2. **24 小时守护未跑满**，只有 4 个点的短跑自检；长稳结论待补。
3. **OCR / ASR 无真实模型**：本机没有 tesseract，`OCR_CLI` 未配置；ASR 只有能量 VAD。
   因此"图片/语音端到端准确率"不在本报告范围内，只有文本判别指标。
4. 白样本误报 4/20 条集中在"客服退款"类正常咨询，精确率 0.833 会随阈值变化，
   正式评审前应固定阈值再复测一次。
5. 压测只覆盖 `/api/v1/detect/text`；`/detect/audio`、`/detect/image` 的时延未测。
